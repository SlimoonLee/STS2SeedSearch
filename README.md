# seedsearch — STS2 离线种子搜索器

基于《Slay the Spire 2》v0.111.0 数据，从种子重放捏奥、第一幕、遭遇队列、地图、问号掷点和战斗奖励；不启动游戏或模拟战斗。CLI 与 WinForms GUI 使用同一个搜索执行器。


## 外部依赖：sts2-cli

本仓库不包含《Slay the Spire 2》的游戏 DLL、Godot 运行库、官方本地化文件或游戏资产。构建奖励对拍测试和 GUI 中文名称需要单独准备 [sts2-cli](https://github.com/iRyougi/sts2-cli)，并让两个仓库并列：

```text
workspace/
├─ sts2-cli/
└─ seedsearch/
```

在 `workspace` 中执行：

```powershell
git clone https://github.com/iRyougi/sts2-cli.git sts2-cli
git clone https://github.com/SlimoonLee/STS2SeedSearch.git seedsearch
```

然后按 `sts2-cli` 的 README 和当前游戏版本说明运行 `setup.sh`，使 `sts2-cli/lib/`、`sts2-cli/src/Sts2Headless/` 和 `sts2-cli/localization_zhs/` 就绪；该步骤需要 Steam 版游戏。最后在 `seedsearch` 目录构建：

```powershell
cd seedsearch
dotnet build -c Release
.\run_gui.cmd
```

`search-config.json` 是当前使用的筛选配置，输出路径已改为仓库内的 `results/` 相对路径；它包含随机键、起始索引和完整筛选条件，便于复现实验。运行前可按需修改 `outFile`。

## 启动

要求 .NET 10 SDK；GUI 运行于 Windows。保留工程已有 `sts2-cli/lib/System.IO.Hashing.dll` 与提取数据。

```powershell
cd seedsearch
.\run_gui.cmd
```

启动器先构建 Release，再打开 GUI；已构建的程序在 `SeedSearchGui/bin/Release/net10.0-windows/SeedSearchGui.exe`。

CLI：

```powershell
dotnet build -c Release
dotnet bin/Release/net10.0/seedsearch.dll search config.example.json
dotnet bin/Release/net10.0/seedsearch.dll validate X6MB8T8NLGQ5
dotnet bin/Release/net10.0/seedsearch.dll dump BBBBBBBBBBB2 Underdocks Silent
```

## 界面

- 左侧“条件”设置职业、进阶、账号状态与路线要求；“范围与文件”设置数量、随机键、起始索引、线程、输入名单和输出；“地图范围”设置简图模式和搜索截止层。
- 右侧标签页分别筛选捏奥、卡牌、Boss 与遭遇条件。支持中文/ID/卡牌来源搜索、全选可见、清空可见和取消全部；隐藏项保留勾选。卡牌列表包括当前职业、无色及其他职业，按来源与稀有度分组；“本职业普通 + 罕见”仅选择当前职业。遭遇页可选择强怪池前缀、第一精英组合，并勾选精英堵路与第一个精英前禁火。
- 切换职业会保存各职业的卡牌选择；Boss 随第一幕切换。空白名单表示不限制。
- “保存配置 / 载入配置”与 CLI 兼容；下次启动恢复上次有效条件。
- 如果配置对应的输出文件旁存在同条件、同随机键和同范围的有效检查点，会启用“从上次继续”并自动沿用原结果文件；修改筛选条件会自动取消这个选项并换用新输出，避免把不同条件接到同一份结果上。检查点损坏但 `.bak` 可用时也会显示为可续搜。
- “仅筛开局”将 X、K 设为 0，跳过建图；仍筛选已应用的捏奥额外卡牌。
- 新建条件默认“搜索简图（精确）”、前 10 层；“前10层”按钮恢复这两个设置，保留其他筛选条件。载入旧配置或恢复上次设置时保留原搜索范围。
- “范围与文件”中勾选“找到一个为止（不限制数量）”，数量输入禁用，持续搜索到一个符合全部条件的种子后保存并自动停止；仍可点击“停止”。
- 搜索时显示评估数、命中数、吞吐、预计剩余时间与各阶段通过数（包括遭遇队列和奖励预筛）；“停止”保存已有结果，关闭窗口也会取消搜索并等待落盘。
- 下方表格显示前 1,000 个命中，选中后显示已应用的捏奥、额外卡牌/全部候选组、变形前后、固定诅咒、路线前缀和后续奖励。支持多选复制种子、双击复制和打开结果目录；所有命中均写入文件。
- 遭遇条件中的强怪、精英名称会在组合名后直接列出游戏配置里的全部可能成员；这是随机组合的候选集合，不把它误标成固定站位。详情还会显示每场药水、精英遗物及宝箱遗物序列。
- GUI 默认使用新输出文件名。CLI 在“自动续跑”开启时保护已有结果；需要从头覆盖时，关闭自动续跑后再启动。

## 条件语义

`character` 支持 Ironclad、Silent、Defect、Regent、Necrobinder；`ascension` 为 0–10，目前仅支持单人、全解锁档案。

`act1` 是第一幕**过滤器**，不是强制指定生成幕：种子 `act_selection` RNG 与暗港账号状态决定第一幕。暗港未解锁只会有密林；已解锁但未发现时强制暗港；均已满足时两幕各 50%。

遭遇条件在建图前读取第一幕队列：`normalStrongAllow` 要求所选强怪全部出现在弱怪之后的强怪池前 `normalStrongPrefixLength` 项内，长度为 0 时按所选组合数量；`firstEliteAllow` 只匹配精英队列第一项。`eliteBlock` 检查完整地图，要求不存在绕过所有精英直达 Boss 的路线；`noRestBeforeFirstElite` 检查路线从起点到首次精英（或直接到 Boss）的前缀，火堆出现在首次精英之前的路线会被淘汰；若首次精英在搜索截止层之后，只继续检查静态地图前缀，不扩大卡牌、奖励或问号的筛选范围。`routeMode="all"` 要求每条路线通过路线条件，`exists` 只需一条；若还要强制所有路线遇到精英，请同时启用 `eliteBlock`。

捏奥正面白名单要求两个正面选项都在其中，诅咒白名单要求第三项在其中。`neowChoice=-1` 不应用效果；0、1、2 分别模拟实际选择的三个展示选项。只有一项正面，或仅选一对互斥遗物，会在搜索前指出条件不可能满足。

要检查捏奥带来的卡牌及后续序列，需在“捏奥白名单”页的“实际选择”指定第 1/2/3 项。只有实际选中的一项执行效果，执行一次后按其状态继续重放战斗；展示但未选择的其他遗物不会改变序列。所有随机生成的候选都须在卡牌白名单内；即使只选其中一张或一组，也检查全部候选。固定诅咒只展示、不筛选。

| 参数 | 含义 |
|---|---|
| `routeMode="all"` | 每条路线的前 X 个房间均为普通战斗、精英或摇出怪物的问号；逐分支检查奖励 |
| `routeMode="exists"` | 存在一条路线，其前 X 场被检查的战斗奖励符合要求 |
| `minFightsChecked` | X；0 表示不检查战斗奖励 |
| `checkFromFirstUnknown` | 仅 exists：true 从第一个问号起检查；false 从开局首场战斗起检查 |
| `unknownMonsterStreak` | K；前 K 个问号均需摇出怪物；all 要求所有路线满足，exists 只需一条 |
| `normalStrongPrefixLength` / `normalStrongAllow` | 强怪池前 N 项必须包含所选小怪组合；N=0 按组合数量，空组合=不限；弱怪不计入 N |
| `firstEliteAllow` | 第一幕精英遭遇队列的第一项必须属于所选组合；空=不限 |
| `eliteBlock` | true 时完整地图上不存在不经过精英即可到达 Boss 的路线；与 Boss 队列筛选独立 |
| `noRestBeforeFirstElite` | true 时路线首次精英前不能出现火堆；all/exists 分别对应每条/至少一条路线；未遇到精英而到达 Boss 的路线需配合 `eliteBlock` 才会被排除 |
| `maxSearchFloor` | 第一幕搜索截止层，1–15，包含该层；第 1 层是开局战斗，捏奥为第 0 层；目标必须在截止层满足 |
| `mapMode` | `search` 默认精确简图，落选种子省去坐标整理；`full` 完整地图，用于对照；命中结果与坐标一致 |
| `allowedCards` | 已选择的捏奥随机卡牌/变形结果及被检查的每场三张奖励卡全部在白名单内；固定诅咒不检查；支持职业、无色、异色牌的类名或 snake ID，空=不限 |
| `threads` | 0 自动使用 CPU 核数，正数指定并行度 |
| `findUntilHit` | true：忽略 count，找到一个即保存并停止；false（默认）：按数量批量搜索 |
| `resumeFromCheckpoint` | true：检测输出文件旁的 `.checkpoint.json` 并跳过已完成块；false：忽略检查点，从当前起始索引重新开始；为避免覆盖已有结果，自动续跑开启且结果文件无检查点时会拒绝启动 |
| `checkpointIntervalSeconds` | 检查点持久化间隔，1–60 秒，默认 2；只影响崩溃后最多重扫的最近未提交块 |
| `rngSeed` / `startIndex` / `count` | 64 位随机键、枚举起点；固定数量模式枚举 `[startIndex, startIndex+count)` |
| `seedListFile` | 输入名单，不使用 count/随机范围；批量模式处理全部非空行，找到为止模式命中即停 |

X=0、K=0 且未启用 `eliteBlock`/`noRestBeforeFirstElite` 时只筛捏奥、第一幕、Boss、遭遇队列及已应用的捏奥额外卡牌，不建图。启用任一精英路线条件仍会建图检查；禁火条件会继续沿路线走到首次精英或 Boss 以确认前缀。Boss 来自独立遭遇队列，在路线建图之前筛选，指定 Boss 不需要地图。旧 `maxRoutes` 字段可读，但不再截断可行路线。

### 捏奥卡牌重放

| 遗物 | 检查内容 | 随机流与后续序列 |
|---|---|---|
| 奥术卷轴 `ArcaneScroll` | 新增 1 张稀有牌 | Rewards 消耗 1 次 |
| 沉重石板 `HeftyTablet` | 三选一的全部 3 张稀有候选；受伤只展示 | Rewards 消耗 3 次；不改变战斗稀有度累计值 |
| 卷轴箱 `ScrollBoxes` | 两组全部 6 张牌 | 通常消耗 6 次；机械人每组有三爪判定，实际消耗为 8/5/2 次 |
| 失物盒 `LostCoffer` | 全部 3 张候选，另展示开局药水 | Rewards 消耗 11 次；不更新战斗卡牌/药水累计赔率 |
| 树叶药膏 `LeafyPoultice` | 起始打击、起始防御的两个变形结果 | Transformations 消耗 2 次；不推进 Rewards |
| 新叶 `NewLeaf` | 选中的起始基础牌的变形结果 | Niche 消耗 1 次；开局各可变基础牌使用相同候选池 |
| 铅制镇纸 `LeadPaperweight` | 全部 2 张无色候选 | Rewards 消耗 6 次 |
| 万花筒 `Kaleidoscope` | 两次奖励的全部 6 张其他职业候选 | Rewards 消耗 18 次，Niche 消耗 6 次 |

进阶 7 起使用游戏的稀缺参数：普通战斗基础稀有率 1.49%、精英 5%、累计增长 0.5%；进阶 0–6 分别为 3%、10%、1%。这也影响失物盒、铅制镇纸、万花筒的非战斗卡牌生成。非战斗奖励采用基础赔率，不读取或更新战斗累计值。

涅奥骨骰 `NeowsBones`、小型扭蛋 `SmallCapsule`、巨大扭蛋 `LargeCapsule` 会继续获得其他遗物，递归效果尚未完整展开。启用卡牌白名单时，实际选择这三项的种子会被排除，避免把未生成/未知卡牌当作通过；若第三项白名单仅包含这些未支持选项，会在开始前报明条件不支持。没有卡牌限制时可筛开局，详情标明重放边界。

### 药水、战斗遗物与宝箱序列

药水不是每场独立的固定概率，而是游戏 `PotionRewardOdds` 的累计赔率。初始值为 40%；普通战斗使用当前值，精英战斗在掷骰阈值上增加 `0.25 × 0.5 = 0.125`。本场出了药水，下一场累计值减 10 个百分点；没出则加 10 个百分点，长期目标约为 50%。强制掉药水的遗物/Hook 会绕过普通掷骰，当前离线重放没有假设这些外部 Hook。

战斗先在同一条 `Rewards` 随机流上掷是否出药，再掷金币；出了药水后才掷药水稀有度：`<=10%` 稀有、`10%–35%` 罕见、其余普通，再从对应的职业池与共享池等概率抽取药水。之后才是三张卡牌以及精英遗物稀有度，所以是否出药、药水种类都会改变同一场后续卡牌的随机位置；后续战斗继续沿用同一条流和累计赔率。GUI 详情中的“药水”已经是实际抽出的物品，而不是只有概率标签。

精英遗物在战斗奖励序列的最后掷一次稀有度：普通 `<50%`、罕见 `<83%`、稀有否则。真正的遗物来自按角色和共享池建立、开局预先洗牌的 `RelicGrabBag`，按稀有度从队首取出且不放回；因此同一稀有度的名称序列由种子、职业、解锁内容和此前已经取走的遗物共同决定。宝箱使用独立的 `TreasureRoomRelics` 随机流掷同样的 `50%/33%/17%` 稀有度，但仍从共享遗物袋取件。详情中的“宝箱奖励序列”按出现顺序列出金币和实际遗物名称。

当前实现已对照 v0.111.0 的药水赔率、药水池、战斗奖励顺序、精英遗物稀有度、宝箱稀有度和遗物袋队首取件逻辑；遗物 `IsAllowed`、强制掉药水 Hook、商店/事件特殊奖励和后续玩家选择仍属于重放边界，游戏更新后应重新提取数据并复核。

## 前 10 层与简图

在 GUI“地图范围”中选择“搜索简图（精确）”，将“搜索截止层”设为 10；CLI 配置对应：

```json
"mapMode": "search",
"maxSearchFloor": 10
```

搜索最迟在第 10 层满足战斗数和问号条件，仍未满足则该路线失败，不再向后遍历。**截止层不是战斗数 X**：X 表示要检查多少场战斗；all 额外要求前 X 个房间全部是战斗。未带 `maxSearchFloor` 的旧配置默认 15，保留原整幕搜索语义；新 GUI 和示例配置默认 10。

精确简图保留整幕房间类型与连边，推迟居中、疏开、拉直等坐标整理，仅命中时补齐，以保持导出坐标与完整地图一致。后半幕的重复路线剪枝、类型补点与 RNG 消耗会影响前 10 层，直接只生成 10 层或略过这些步骤会改变结果，因此仍重放整幕的必要逻辑。路段比较改用精确的 128 位类型编码，减少临时数组与重复扫描；引擎剪枝顺序保持一致。

搜索按索引生成合法 12 位种子，同一随机键内不重复，结果集合不依赖线程数；JSONL 行序随并行调度变化。输入种子与游戏一致：大写、去两端空白、I→1、O→0。

配置中的相对路径按**配置文件所在目录**解析。输入输出相同路径会在写入前拒绝。输出保留 `seed/act1/boss/neowA/neowB/neowC/route/unknownRolls/fights/checkedFights/treasures` 等字段，路线只记录已经验证的前缀；应用捏奥时另有 `neow`，记录遗物、卡牌及候选组、变形来源、药水和 `exact`。未应用时省略该字段。

## 找到一个为止

在“范围与文件”勾选“找到一个为止（不限制数量）”，设置筛选条件后点击“开始搜索”。CLI 配置设置 `"findUntilHit": true`。原来的 `count` 不参与数量限制，保留以便切回批量模式；该选项也会随配置保存和恢复。

枚举从 `startIndex` 开始使用当前 `rngSeed` 持续生成新种子，直到找到一个符合所有条件的结果或手动停止。运行时显示已评估数量、命中数和速度，使用滚动进度条，不显示固定总数或预计剩余时间。GUI“停止”或 CLI Ctrl+C 均可结束搜索。

多线程可能有少量已开始的评估需要收尾，但只保存、显示和回调一个命中；选取先完成筛选的种子，不保证是最小索引。阶段“条件通过”统计包括其他已开始的评估，保存命中数仍为 1。自动找到与手动取消分别显示，不把找到后的正常停止当作取消。

如果指定输入名单，仅搜索该名单，命中即停，未命中则在名单末尾结束；清空输入名单即可持续枚举新种子。12 位种子空间自然用尽时也会结束，不循环重复同一批候选。旧配置没有此字段时仍按原数量批量搜索。

## 批量搜索与复筛

可以直接使用严格条件一次搜索，奖励白名单会在能够确定奖励序列时先于建图执行。需要反复调整条件时，可保存开局候选再复筛：

1. 点击“仅筛开局”，设置 Boss/捏奥/第一幕，输出至 `coarse.jsonl`。
2. 将它选为“输入名单”，恢复 X 和卡牌条件，输出选择另一个文件。

名单支持每行一个裸种子，或搜索器的 JSONL 命中记录。输入数量不限于 count。

随机范围搜索会在输出文件旁保存 `<outFile>.checkpoint.json`，同时保留一个 `.bak`。停止、断电或异常后，保持相同筛选条件、随机键、范围和输出文件再次启动，会直接枚举未完成的范围，不从零扫描已完成的块；当前检查点之后尚未提交的结果会安全回退并重放，默认最多约 `checkpointIntervalSeconds` 秒的进度。检查点带配置指纹、范围校验、校验和、输出字节数和尾部摘要；结果文件多出的未提交尾部会自动截断，文件变短或校验不符时会拒绝续跑，避免静默漏搜。改动筛选条件时会拒绝误续跑；关闭 `resumeFromCheckpoint` 可明确从头开始并覆盖结果文件。没有检查点但结果文件已有内容时，自动续跑也会拒绝启动。完整完成一个随机范围后主检查点删除，备份保留。名单模式不使用检查点，已有结果文件也不会被自动覆盖。

每个输出文件还会有 `<outFile>.lock`（防止两个进程同时写入）和 `<outFile>.errors.jsonl`（记录配置、范围、进度、异常堆栈与恢复事件）。配置文件保存采用原子替换并保留 `.bak`；主配置损坏时载入会尝试备份。

## 性能与验证

本机相同有效种子的 Release 单线程对照：建图并检查 all/X=2 从约 **74/s 提升到 224/s（3 倍）**，每种子临时分配减少约 **84%**；加示例 20 张卡白名单从约 **77/s 提升到 23,855/s**，主要因多数种子在建图前被奖励预筛淘汰。实际吞吐取决于筛选条件和硬件。

全空间枚举不会为每个未命中候选创建种子字符串：索引置换后的 12 位直接写入栈缓冲并计算 XXHash，命中写出时才恢复种子文本。奖励白名单会在发现首张不合格卡牌后短路；没有 Boss/遭遇队列条件时，确定的普通奖励预筛会先于遭遇队列和地图生成。当前 Release 的 `Tests/benchmark` 单线程短基准（同一进程、无磁盘写入）约为粗筛 **14 万 seeds/s**、建图 all/X=2 **300–470 seeds/s**、白名单 all/X=2 **5–7 万 seeds/s**；实际吞吐取决于筛选条件和硬件。历史的 100 万命中 JSONL 测量约 **67,025 seeds/s**，仅用于说明直接哈希路径，不能与上述内存基准直接比较。

## 批量 SIMD / GPU 评估

本机检测到 SSE2、AVX、AVX2 和 AVX-512F，但完整筛选不是规则的同构循环：每颗种子有独立的 Xoshiro 状态、加权遭遇 GrabBag、卡牌稀有度 pity、捏奥分支和路线 DFS，且多数阶段会提前淘汰。把这些状态压成 SIMD lane 会产生大量分支发散，GPU 还要复制整套游戏数据和随机流，结果校验成本会超过短输入哈希的收益。

因此当前落地的是精确的批量块调度和队列摘要：随机空间按 4,096 候选成块并行，块内保持原顺序，完整块才能提交结果和检查点。`QueueGen.GenerateSummary` 以低分配方式用相同 RNG 计算 Boss、先古、强怪前缀和第一精英；奖励预筛前不创建完整遭遇列表，且无捏奥需求时跳过遗物桶对象、只保留等量 RNG 消耗。奖励通过后才完整生成队列和地图；256 个跨两幕种子已对拍摘要与完整队列。12 字节种子哈希走 `System.IO.Hashing.XxHash64` 的短消息路径；索引置换和 Base34 编码的 `UInt128` 取模仍是标量，未强行加入会改变结果或增加维护成本的自定义 SIMD/GPU 内核。后续若要继续扩展，优先方向是把捏奥/第一幕/Boss 这类无地图粗筛拆成独立批处理，再用命中集合回到 CPU 精确重放；当前版本不引入 GPU 运行时依赖。

若没有捏奥筛选、也没有指定实际选择，三项捏奥展示结果会延迟到最终命中才生成；这只减少落选候选的对象和字符串工作，不改变 RNG 或命中报告。

后续简图及路段编码优化，在 1,024 个相同种子的独立基准中，all/X=2 从上一版 **312/s 到 396/s**，分配再减少约 **28%**，192 个命中的完整 JSON 一致。坐标整理仅占部分成本，简图相对当前 full 的吞吐收益随条件和测量波动变化；完整对照见审查记录。

以上是当时奖励模型下的历史性能对照。此次修正了进阶 7 以上的卡牌赔率，当前 A7+ 的奖励/白名单命中可能与历史旧程序集不同，不能再用旧模型要求完整奖励 JSON 相等。

## 重放边界

基于现有版本数据，假设全 Epoch 解锁、单人 slot 0、非教学局、无 Modifiers/自定义局。商店和事件选择的奖励流消耗未展开；在所需战斗检查完成前遇到这些房间会停止精确跟踪，无法据此确认后续奖励。

战斗使用全杀、GoldProportion=1 假设；部分遗物钩子和玩家后续选择未完整建模。上述八项捏奥卡牌生成已实际重放，其他遗物仍使用现有消耗模型；后续取得遗物的特殊钩子、额外卡牌/战斗中生成牌尚未完整跟踪。问号逻辑沿用已有赔率机，仍需游戏内导航对拍。游戏更新后需重新生成数据并重新验证。

数据生成入口：`tools/extract_gamedata.py`；产物：`src/GameData.g.cs`。
